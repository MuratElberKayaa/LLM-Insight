- **Actions:** `actions/checkout` and `actions/setup-python` use the existing pins, Python 3.12.6.

  - The commit is dated 2026-10-07T10:00:52Z and shows GitHub "verified". The tag is identical to `main` of that repository. The action runs on node24.
- **Steps:**
  1. **Security tool environment.** Creates a venv in `$RUNNER_TEMP/audit-venv` and installs it from the lock with `--require-hashes --no-deps --only-binary :all:`. Then runs `pip check` and `pip_audit_gate.py check-env` (installed set equals the lock) and checks that `pip-audit --version` equals `pip-audit 2.10.1`. Nothing is installed into a project venv.
  2. **Audit gate self-tests (offline).** `python -I -m unittest discover -s scripts/qa/tests -v` runs 18 tests.
  3. **Python dependency audits.** Four runs, `backend` and `sdk` lockfiles × `pypi` and `osv`. Each run is:
     ```
     timeout 240 pip-audit -r <lock> --no-deps --disable-pip -s <service> --progress-spinner off \
       --format json -o "$RUNNER_TEMP/pip-audit-raw/<id>.json" --cache-dir "$RUNNER_TEMP/pip-audit-cache" \
       2> <id>.stderr.txt
     ```
     Each run's exit status is written to `<id>.exit`, with run ids `backend-pypi`, `backend-osv`, `sdk-pypi` and `sdk-osv`. Every run executes even if an earlier one finds something, using the same `status=$?` recording pattern as the npm full audit. This step itself does not decide the result.
  4. **Python dependency audit gate.** `python -I scripts/qa/pip_audit_gate.py evaluate` evaluates all four runs and fails the job unless every run is PASS.
  5. **Upload.** `if: always()`, artifact `pip-audit-reports`, `if-no-files-found: error`, `retention-days: 14`. An upload failure fails the step; it is not silenced.
- **Not used:** `--fix`, `--ignore-vuln`, `--skip-editable`. There is no accepted Python advisory.

### 5. Gate `scripts/qa/pip_audit_gate.py`

- **Design:** stdlib only, no subprocess, no network. It reads only the files written by step 3.
- **Why it classifies:** pip-audit 2.10.1 exits 1 for findings and for errors alike (measured, §7), so the result class comes from the report and stderr, never from the exit status alone.

| Status | Condition |
|---|---|
| PASS | exit 0; report has exactly `{dependencies, fixes}`, empty `fixes`; every dependency has `name`, `version`, `vulns` and nothing else; the reported `name → version` set equals the lockfile's pins exactly (no missing, extra, duplicate or different version); no skip; no vulnerability |
| VULNERABLE | at least one advisory, whatever the exit status; findings deduplicated by (package, version, id, aliases) |
| SERVICE_UNAVAILABLE | no report and stderr shows a `requests`/`urllib3` connection, proxy, timeout or service error |
| INVALID_LOCKFILE | the lockfile is missing or not a list of exact `name==version` pins (checked by the gate itself), or pip-audit rejected it |
| TIMEOUT | exit status 124 from `timeout` |
| NOT_AUDITED | pip-audit skipped a dependency (`skip_reason`) |
| MALFORMED_REPORT | not JSON, unexpected keys or types, or a report that does not cover the lockfile exactly |
| TOOL_FAILURE | exit status not recorded, no report without a known cause, or a clean report with a non-zero exit |

- **Outputs:**
  - `summary.json` and `summary.md`, one row per run: target, service, status, number of vulnerabilities, package, version, advisory id and aliases.
  - `summary.md` is also appended to `$GITHUB_STEP_SUMMARY`.
  - `::error::` annotations for every failing run.
- **Report safety:** only reports whose shape passed the allowlist are copied to the upload directory. A malformed report is never uploaded. Stderr is copied truncated to 64 KiB.

### 6. Checker `scripts/qa/bandit_baseline_check.py`

- **Design:** stdlib only, no subprocess, no network. It reads the recorded report, exit status and stderr, the baseline, the register and the checked-out sources (to recompute the fingerprints itself).
- **Subcommands:**
  - `validate-baseline`;
  - `evaluate`;
  - `candidates` and `register`, which are local review aids.

| Problem | Fails when |
|---|---|
| BASELINE_MISSING / BASELINE_MALFORMED / BASELINE_INVALID | no file, not JSON, any schema deviation (keys, types, digests, paths, origins, totals ≠ entries, tool ≠ 1.9.4) |
| BASELINE_DUPLICATE | repeated id or repeated (fingerprint, occurrence) |
| UNKNOWN_CLASSIFICATION | class outside the closed set or not covering the entry's test, severity or path |
| REGISTER_MISSING / REGISTER_MALFORMED / REGISTER_MISMATCH | `SECURITY.md` register absent, unparsable, or not equal to the baseline |
| TOOL_FAILURE | exit status missing, 124 (timeout), not 0/1, inconsistent with the results (exit 0 with findings, exit 1 without); stderr missing or not empty |
| REPORT_MISSING / MALFORMED_REPORT | no or empty report; not JSON; any unexpected key or type; metrics not adding up; a finding not matching the checked-out source |
| SKIPPED_FILE | any `errors` entry (a file Bandit could not scan) |
| NOSEC | any `nosec` or skipped test in the metrics |
| TARGET_MISSING / CONFIG_FILE | a target directory absent; a `.bandit` file inside a target |
| UNSCANNED_FILE / UNEXPECTED_SCOPE | the scanned file set differs from an independent walk of the targets (every `*.py`, `*.pyw`); a scanned file outside them; `--target` differs from the baseline scope |
| NEW_FINDING | a finding at any severity without an entry |
| CHANGED_FINDING | an entry matched by fingerprint and occurrence whose test name, severity, confidence, CWE, statement hash or issue-text hash differs |
| MISSING_FINDING | an entry with no current finding: a removed finding must be deleted from the baseline and the register in a reviewed change; a stale entry is never accepted |

- **Matching:** the current findings and the entries must be equal as multisets of (fingerprint, occurrence). A line move alone passes and is shown as `baseline_line` in the summary.
- **Counts are reported, never used to decide.** A swap of one finding for another with the same total fails (§7, §9).
- **Outputs:** `summary.json` and `summary.md`, also appended to `$GITHUB_STEP_SUMMARY`, and `::error::` annotations. A non-empty stderr is printed to the job log, truncated to 64 KiB. The checker uploads nothing itself.

- `config --quiet` and `--no-interpolate` keep resolved values out of output and files (LOCALLY EXECUTED on synthetic values: the value was absent from the rendered model).

### 6. Build-context safety

- **Gap found and corrected.** A pattern such as `.env` applies only at the context root, and the root file's `!backend/app/` re-included everything below it, so a local `backend/app/.env` would have entered the backend image. `**/.env` and `**/.env.*` were added to `.dockerignore` and `frontend/.dockerignore`, after the allow lines. No tracked file matches them, and nothing else was changed in either file.
- **Root context:** deny-all with a narrow allow list, so Git history, the handoff and Phase 7 files, virtual environments, `node_modules` and caches are all excluded (STATIC CHECK ONLY, using a matcher that follows Docker's documented rules).
- **Frontend context:** root is `frontend/`, so root-level files and `.git` are outside it; `node_modules`, `.next`, `.test-build`, `test-results`, `playwright-report` and `.env*` are excluded (STATIC CHECK ONLY).
- **On the runner (not yet executed):** preflight plants a random canary in eight paths that must stay out of the images: nested `.env` files in both contexts, `frontend/.env.local`, and the three user-owned file names. Those files exist only in the ephemeral checkout, and an existing file is never overwritten. `verify` then reads every layer of `docker image save` for the backend, frontend and frontend build stage and fails on the canary, on any generated secret value, or on an excluded path inside the application tree.

**Building an image does not prove that the application runs.** Startup, migrations and E2E behaviour remain separate; R104-5 is not started.
