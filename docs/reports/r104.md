- **Roots:** `pip-audit==2.10.1` and `bandit==1.9.4`. Bandit is locked for R104-2 only; this step adds no Bandit gate.
- **Closure:** 32 packages, including `pip`, which `pip-api` requires. This is a complete transitive closure for CPython 3.12.6 on Linux x86_64.
- **Generation:** done in a throwaway `docker run --rm` container from `python:3.12.6-slim-bookworm` (`sha256:ad48727987b2…`, linux/amd64, pip 24.2), never with the project's compose stack.
  1. Resolve:
     ```
     python -m venv /v
     /v/bin/python -m pip install --dry-run --ignore-installed --only-binary :all: \
       [-c constraints.txt] --report resolve.json "pip-audit==2.10.1" "bandit==1.9.4"
     ```

  3. Check the version's first upload time, its yanked status and each file's upload time.

  5. Write the lock from PyPI's published SHA-256 of every non-yanked file of that version uploaded before the cutoff. That gives 457 hashes: universal wheels plus the platform wheels of `charset-normalizer`, `msgpack`, `pyyaml` and `tomli`, and the sdists. No hash was computed or typed by hand.

### 3. Toolchain verification (local, Linux container)

In a fresh `python:3.12.6-slim-bookworm` container:

- Install: `python -m pip install --require-hashes --no-deps --only-binary :all: -r security/tools/requirements-audit.lock` → exit 0.
- Versions:
  - `pip --version` → 26.2.2 (the venv's 24.2 is replaced from the lock);
  - `pip-audit --version` → `pip-audit 2.10.1`;
  - `bandit --version` → `bandit 1.9.4`.
- `pip check` → "No broken requirements found."
- Imports of `pip_audit`, `bandit`, `cyclonedx`, `cachecontrol`, `pip_api`, `pip_requirements_parser`, `requests`, `rich`, `yaml`, `stevedore`, `msgpack`, `platformdirs` and `filelock` all succeed.
- Installed set equals the lock (`pip_audit_gate.py check-env`): 32 pins, 32 installed, none missing, none extra, no version differs.
- **Tamper test:** with every hash of `bandit` replaced by zeros, the install is refused (exit 1, "THESE PACKAGES DO NOT MATCH THE HASHES") and `bandit` is not importable. Replacing only one of a package's two hashes is accepted, because pip accepts any listed hash, so the test changes all of a package's hashes.

### 4. CI job `security-python` (`.github/workflows/ci.yml`)

- **Runner and environment:**
  - `ubuntu-24.04`, `timeout-minutes: 10`, `permissions: contents: read`;
  - no `needs` or `if` on the job, so it runs independently of `docs`, `python` and `frontend`;
  - no `continue-on-error`;
  - no secrets, no `.env`, no database.
- **Actions:** `actions/checkout` and `actions/setup-python` use the existing pins, Python 3.12.6.
  - New: `actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9`, tag `v7.0.2`, a lightweight tag on that commit.
  - The commit is dated 2026-10-07T10:00:52Z and shows GitHub "verified". The tag is identical to `main` of that repository. The action runs on node24.
- **Steps:**
  1. **Security tool environment.** Creates a venv in `$RUNNER_TEMP/audit-venv` and installs it from the lock with `--require-hashes --no-deps --only-binary :all:`. Then runs `pip check` and `pip_audit_gate.py check-env` (installed set equals the lock) and checks that `pip-audit --version` equals `pip-audit 2.10.1`. Nothing is installed into a project venv.
  2. **Audit gate self-tests (offline).** `python -I -m unittest discover -s scripts/qa/tests -v` runs 18 tests.
  3. **Python dependency audits.** Four runs, `backend` and `sdk` lockfiles × `pypi` and `osv`. Each run is:
     ```
     timeout 240 pip-audit -r <lock> --no-deps --disable-pip -s <service> --progress-spinner off \
       --format json -o "$RUNNER_TEMP/pip-audit-raw/<id>.json" --cache-dir "$RUNNER_TEMP/pip-audit-cache" \
       2> <id>.stderr.txt
     ```
     Each run's exit status is written to `<id>.exit`, with run ids `backend-pypi`, `backend-osv`, `sdk-pypi` and `sdk-osv`. Every run executes even if an earlier one finds something, using the same `status=$?` recording pattern as the npm full audit. This step itself does not decide the result.
  4. **Python dependency audit gate.** `python -I scripts/qa/pip_audit_gate.py evaluate` evaluates all four runs and fails the job unless every run is PASS.
  5. **Upload.** `if: always()`, artifact `pip-audit-reports`, `if-no-files-found: error`, `retention-days: 14`. An upload failure fails the step; it is not silenced.
- **Not used:** `--fix`, `--ignore-vuln`, `--skip-editable`. There is no accepted Python advisory.

### 5. Gate `scripts/qa/pip_audit_gate.py`

- **Design:** stdlib only, no subprocess, no network. It reads only the files written by step 3.
- **Why it classifies:** pip-audit 2.10.1 exits 1 for findings and for errors alike (measured, §7), so the result class comes from the report and stderr, never from the exit status alone.

| Status | Condition |
|---|---|
| PASS | exit 0; report has exactly `{dependencies, fixes}`, empty `fixes`; every dependency has `name`, `version`, `vulns` and nothing else; the reported `name → version` set equals the lockfile's pins exactly (no missing, extra, duplicate or different version); no skip; no vulnerability |
| VULNERABLE | at least one advisory, whatever the exit status; findings deduplicated by (package, version, id, aliases) |
| SERVICE_UNAVAILABLE | no report and stderr shows a `requests`/`urllib3` connection, proxy, timeout or service error |
| INVALID_LOCKFILE | the lockfile is missing or not a list of exact `name==version` pins (checked by the gate itself), or pip-audit rejected it |
| TIMEOUT | exit status 124 from `timeout` |
| NOT_AUDITED | pip-audit skipped a dependency (`skip_reason`) |
| MALFORMED_REPORT | not JSON, unexpected keys or types, or a report that does not cover the lockfile exactly |
| TOOL_FAILURE | exit status not recorded, no report without a known cause, or a clean report with a non-zero exit |

- **Outputs:**
  - `summary.json` and `summary.md`, one row per run: target, service, status, number of vulnerabilities, package, version, advisory id and aliases.
  - `summary.md` is also appended to `$GITHUB_STEP_SUMMARY`.
  - `::error::` annotations for every failing run.
- **Report safety:** only reports whose shape passed the allowlist are copied to the upload directory. A malformed report is never uploaded. Stderr is copied truncated to 64 KiB.

### 9. Remaining limitations

- **GitHub CI not run.** `actions/upload-artifact` and the `ubuntu-24.04` runner image (its preinstalled `timeout` and network access to PyPI and OSV) were not exercised; the local runs used Debian bookworm.
- **Environment audit not included.** Installed environments (`pip-audit --path`) are not audited. The venv bootstrap `pip` 24.2 (R75) is not a gate here, and any such exception would need its own expiring policy. The tool venv itself runs `pip` 26.2.2 from the lock.
- **Out of scope:** the project lockfiles still pin versions without hashes (R75, unchanged); the CPython patch level and OS packages of images are not scanned.
- **Lock scope:** the tool lock is Linux x86_64 and CPython 3.12.6 specific. Its hashes also cover the other platforms' wheels of the same versions, but those were not install-tested.
- **Service dependence:** PyPI and OSV advisory data change over time. A new advisory turns the gate red without any repository change, by design.
- **Lint coverage:** the new gate and its tests are not yet in a CI lint step. The `python` job lints only `scripts/dev` files; they were linted locally with the project's Ruff 0.17.0.
